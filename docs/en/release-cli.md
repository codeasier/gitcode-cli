# Release workflows

Use these commands directly with `gc` (or `gitcode` on Windows); the optional `gh` proxy does not forward them to GitCode.

```sh
gc release list -R org/project --limit 20 --exclude-pre-releases
gc release view -R org/project --json tagName,name,assets
gc release download v1.0 -R org/project -p '*.whl' -D dist
gc release download -R org/project --archive zip -O source.zip
gc release create v1.0 -R org/project --verify-tag --title '1.0' --notes-file NOTES.md
gc release upload v1.0 -R org/project dist/project.whl
gc release edit v1.0 -R org/project --notes-file updated.md
gc release delete-asset v1.0 project.whl -R org/project
```

- An omitted tag selects GitCode's `latest` query, **not** the first page of releases or the most recently updated one. Passing the literal tag `latest` queries by tag. List order is requested from GitCode; prerelease filtering happens before the limit.
- The API returns generated source archives beside user attachments. Ordinary downloads and JSON asset lists exclude the source archives. Use `--archive zip|tar.gz` for a source archive; uploading a file ending in `.zip` does not make it a source archive. A latest download requires a pattern or archive selection.
- Downloads request temporary links, stream without GitCode credentials, and validate a supplied byte length and SHA-256 before installing each file. These checks are **not cryptographic release attestations**; when no digest is reported, no digest comparison is possible. Unknown storage hosts, dangerous names, redirects to untrusted destinations and ambiguous names fail closed. Binary transfers go directly to allowlisted GitCode/AtomGit or Huawei OBS HTTPS hosts, not through the metadata client or environment proxies. Private source downloads may fail if the provider does not issue a usable signed URL. The CLI does not retry with the user's token against storage hosts.
- The filesystem mode is currently POSIX-only: downloads to files and uploads require no-follow directory descriptors. Use regular files under trusted, non-symlink paths. The download directory cannot be shared-writable; use a private subdirectory instead. On other platforms, metadata-only commands and `download --output -` do not use those POSIX filesystem operations.
- Existing files are retained unless `--clobber` is explicit. `--skip-existing` skips existing regular files without revalidating their contents. On interruption, the current partial file is not installed. In a multi-asset transfer, already completed files remain. `--output -` stages and verifies a single asset before writing it to redirected stdout, never a terminal.
- Create publishes immediately. If the tag does not exist, GitCode's creation API may create it at `--target` or the default branch. Use `--verify-tag` for an exact preflight lookup (not an atomic server-side precondition). Files supplied to create upload **after** the release is published; a failed attachment does not roll back the release.
- Local uploads stage a private snapshot of every input before publishing or deleting anything. Symlinks and case/Unicode-normalized collisions are refused. Temporary storage must have space for the selected files. Upload then requests a signed PUT, then checks callback registration by name and compares size/digest where reported. Duplicate names are refused unless `upload --clobber` explicitly requests a non-atomic replacement: deletion precedes upload, and a failed replacement may leave no attachment. Inspect the reported remote state before retrying.
- Create and edit report success only when GitCode returns the requested title, notes and any explicit status, or one follow-up read confirms them. An unverified write must be inspected before retrying. GitCode requires both name and body on edits. Before PATCH, the command reads the release and preserves omitted fields; the API does not document a conditional update for concurrent edits. `--prerelease` and `--latest` are mutually exclusive GitCode states. A missing web URL is null in JSON; `view --web` explains when it opens the repository release list instead.
- There is no standalone release deletion in the documented v5 surface. Deleting a tag to mimic it is unsafe. Drafts, discussion categories, release attestations, generated notes, relabeling uploads, and explicit false variants of status flags are not claimed as compatible.

Contracts: GitCode documents [list](https://docs.gitcode.com/en/docs/apis/get-api-v-5-repos-owner-repo-releases/), [latest](https://docs.gitcode.com/en/docs/apis/get-api-v-5-repos-owner-repo-releases-latest/), [per-tag selection](https://docs.gitcode.com/docs/apis/get-api-v-5-repos-owner-repo-releases-tags-tag/), [temporary download URLs](https://docs.gitcode.com/en/docs/apis/get-api-v-5-repos-owner-repo-releases-tag/), [creation](https://docs.gitcode.com/docs/apis/post-api-v-5-repos-owner-repo-releases/), [editing](https://docs.gitcode.com/docs/apis/patch-api-v-5-repos-owner-repo-releases-tag/), [signed uploads](https://docs.gitcode.com/docs/apis/get-api-v-5-repos-owner-repo-releases-tag-upload-url/) and [attachment deletion by ID](https://docs.gitcode.com/en/docs/apis/delete-api-v-5-repos-owner-repo-releases-tag-attach-files-attach-file-id/). The [AtomGit response definitions](https://atomgit-api-doc.atomgit.com/en/14.release/221.get_the_latest_release_of_the_repository.html) distinguish SOURCE and ATTACH_FILE and document the optional temporary URL field.

## Check a local attachment without downloading it

`gc release check-digest TAG PATH -R OWNER/REPO` is a native, read-only checksum comparison, **not** `gh release verify` or `verify-asset`. Supply an exact tag and a trusted, regular local file (POSIX, up to 1 GiB); its basename must exactly match one uploaded attachment. The command reads [release-by-tag metadata](https://docs.gitcode.com/docs/apis/get-api-v-5-repos-owner-repo-releases-tags-tag/) once, without requesting a download ticket, following any returned URL, or sending the local file or filename.

The [GitCode by-tag schema](https://docs.gitcode.com/docs/apis/get-api-v-5-repos-owner-repo-releases-tags-tag/) lists `digest` (SHA-256) as optional. The [AtomGit by-tag schema](https://atomgit-api-doc.atomgit.com/14.release/222.get_repository_release_by_tag_name.html) does not list it, and its example omits `type` too. A usable digest and attachment type are not guaranteed. This command requires a positive ID, explicit `ATTACH_FILE` and provider SHA-256. If size is provided, it must also match. Missing fields, source archives, ambiguous names and mismatches return nonzero. It neither writes the file nor proves signer identity, attestation, immutability, or that metadata remained unchanged after the read.
